# IGNIS 0G backend

Frontend запускается через `../compose.yaml` из корня workspace; API и PostgreSQL остаются в этом Compose-проекте. Общая инструкция — в [README workspace](../README.md).

API каталога читает данные из локального PostgreSQL. Пустая база возвращает пустой каталог. Чат использует RAG по индексированным источникам. На отдельное приветствие сервер отвечает локально.

## Запуск через Docker

```bash
docker compose up --build -d --wait
curl -fsS http://127.0.0.1:8000/health
```

Compose запускает PostgreSQL, применяет миграции и поднимает API. Swagger доступен на http://127.0.0.1:8000/docs. Для остановки используйте `docker compose stop`.

## Тестовый чат

Откройте `http://127.0.0.1:8000/chat`. Страница загружает исследования из каталога, отправляет вопросы в API на том же адресе и показывает цитаты. При запуске через LAN используйте `http://172.16.11.201:8000/chat`.

## Запуск API на хосте

```bash
python3 -m venv .venv
. .venv/bin/activate
pip install -r requirements.lock
pip install --no-deps -e .
uvicorn app.main:app --reload
```

Интерактивный контракт: http://127.0.0.1:8000/docs. Целевая схема БД и полный контракт, включая P1 и импорт, зафиксированы в [архитектуре](docs/ARCHITECTURE.md) и [спецификации API](docs/API_SPEC.md). Доступны каталог, наборы данных, отдельные маршруты источников, выводов и медиа, а также проверенные связи и граф Nexus. Сравнение пока возвращает `insufficient_evidence`. `/health` проверяет PostgreSQL через SELECT 1 и возвращает 503 при недоступности БД.

## Схема PostgreSQL

Задайте `DATABASE_URL` с драйвером asyncpg, например `postgresql+asyncpg://user:password@localhost:5432/ignis`, затем выполните `alembic upgrade head`. Для отката: `alembic downgrade base`. API использует DATABASE_URL из окружения; по умолчанию подключается к локальному Compose на порту 55432.

Миграция создаёт таблицы studies, sources, findings, datasets, media и relations. Принадлежность источника одной из сторон relation проверяется импортёром. Миграция `0002_chunks` включает pgvector и создаёт таблицу `chunks`. Миграция `0003_embedding_dimension_1024` задаёт размерность 1024 для Alem. Индексация запускается отдельно.

## Локальная база данных

Нужны Docker и Docker Compose. Данные хранятся в Docker-томе `postgres_data` и сохраняются после остановки контейнера.

```bash
docker compose up -d --wait db
DATABASE_URL=postgresql+asyncpg://ignis:ignis_local@127.0.0.1:55432/ignis .venv/bin/alembic upgrade head
```

Адрес доступен только на этом компьютере; `ignis_local` — пароль исключительно для локальной разработки. После изменения `POSTGRES_PASSWORD` в окружении используйте тот же пароль в `DATABASE_URL`; пароль существующего тома автоматически не меняется. Остановить базу: `docker compose stop`. После запуска БД и миграции `/health` возвращает 200.

## Проверки

После запуска БД и миграции выполните `.venv/bin/python -m pytest -q`. Зависимости для тестов входят в `requirements.lock`. GitHub Actions запускает тесты на чистой PostgreSQL и проверяет применение и откат миграций. Интеграционные данные создаются в транзакции и откатываются.

## Импорт исследовательских данных

Подготовьте JSON по разделу 10 `docs/API_SPEC.md`. Из корня репозитория:

```bash
.venv/bin/python -m scripts.import_studies /path/to/studies.json --dry-run
.venv/bin/python -m scripts.import_studies /path/to/studies.json
```

Обе команды используют ту же `DATABASE_URL`, что и API. `--dry-run` валидирует пакет и ссылки относительно пакета и текущей БД, без записи. Обычный импорт выполняется одной транзакцией; при ошибке пакет не записывается частично. Повторная загрузка обновляет записи по стабильным ключам, сохраняя UUID. Отсутствующие в новом пакете объекты не удаляются; optional поля переданных объектов получают контрактные defaults.

Проверяются дубликаты ключей, HTTP(S) URL, ссылки на источники и исследования, числовые ряды и обязательные пояснения для digitized/derived. Исходный текст хешируется; `indexed_hash` импортёр не меняет, поэтому изменённый текст требует переиндексации. Проверка достоверности научных утверждений и разрешение `verified=true` остаются ответственностью человека: импортируйте только проверенные материалы. Демонстрационные данные в тестах синтетические и не загружаются в рабочую базу.

### Дополнительные страницы и медиа workspace

В workspace есть отдельный импортёр, который добавляет 7 обзорных страниц и 24 файла из `nasa-combustion-media-collection/` к уже существующим исследованиям, не создавая новых study-записей. Он использует уникальные ключи и сохраняет UUID при повторном запуске:

```bash
.venv/bin/python -m scripts.import_nasa_collection --dry-run
.venv/bin/python -m scripts.import_nasa_collection
docker compose exec -T api python -m scripts.index_sources
```

Media URL указывают на локальный frontend `http://127.0.0.1:8080/nasa-content/`; frontend Compose монтирует коллекцию только для чтения. Для другого адреса задайте `--public-base-url` импортеру и настройте frontend serving URL соответственно.

## Доступ к локальной базе из LAN

На текущем хосте доступ включён для подсети `172.16.11.0/24`. Команда подключается к `172.16.11.201:55432`, база `ignis`, пользователь `ignis_lan` с правами чтения. Пароль хранится локально в `~/.config/ignis/lan-db.txt`. Передавайте его лично.

Перед включением LAN на новом хосте создайте отдельную роль с правами чтения и добавьте в начало `pg_hba.conf` правила для своей подсети. Первое разрешает этой роли подключение к `ignis` через SCRAM, второе отклоняет остальных пользователей из подсети:

```text
host ignis ignis_lan 172.16.11.0/24 scram-sha-256
host all all 172.16.11.0/24 reject
```

Перезагрузите конфигурацию PostgreSQL. После этого подключите Compose-файл с LAN-адресом:

```bash
IGNIS_LAN_IP=172.16.11.201 docker compose -f compose.yaml -f compose.lan.yaml up -d --wait db
```

Для отключения LAN запустите `docker compose up -d --wait db` без дополнительного файла. После смены IP проверьте адрес и подсеть перед повторным запуском.

## Доступ к API из LAN

```bash
IGNIS_LAN_IP=172.16.11.201 docker compose -f compose.yaml -f compose.lan.yaml up --build -d --wait
```

Swagger доступен по `http://172.16.11.201:8000/docs`, базовый URL API — `http://172.16.11.201:8000/api/v1`. Если фронтенд открыт на другом origin, укажите его в `CORS_ORIGINS` перед запуском Compose. API внутри Docker подключается к PostgreSQL по имени сервиса `db`.
## Индексация и чат

Настройте `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL` по `.env.example`.
Для Alem задайте отдельные ключи `LLM_API_KEY`, `EMBEDDING_API_KEY` и
`RERANKER_API_KEY`. Модели в примере — `qwen3-8`, `text-1024` и
`reranker`. Модель эмбеддингов должна возвращать **1024** измерения. Адаптер
для `text-1024` использует её собственную размерность. Параметр
`EMBEDDING_SEND_DIMENSIONS=true` включает передачу `dimensions=1024`
для совместимых API. Миграция сохраняет существующие векторы размерности 1024. Если в базе есть векторы другой размерности, она откатится.

```bash
set -a
. ./.env
set +a
alembic upgrade head
python -m scripts.index_sources --check-provider
python -m scripts.import_nasa_kb /path/to/nasa-fire-safety-kb --dry-run
python -m scripts.import_nasa_kb /path/to/nasa-fire-safety-kb
python -m scripts.index_sources
uvicorn app.main:app
```

Для Gemini Flash-Lite через OpenRouter задайте `LLM_BASE_URL=https://openrouter.ai/api/v1`,
`LLM_MODEL=google/gemini-2.5-flash-lite` и ключ OpenRouter в `LLM_API_KEY`.
Ключи эмбеддингов и reranker задаются отдельно. `RAG_MAX_OUTPUT_TOKENS`
ограничивает длину генерации, по умолчанию 3200 токенов.
Чат учитывает контекст диалога и запрошенную глубину ответа. Ссылки в тексте
соответствуют проверенным фрагментам из БД. Поле `suggested_questions`
содержит до двух коротких вопросов для продолжения разговора, если их
подсказывает найденный контекст.

Ассистент объясняет термины и базовые научные принципы из общих знаний,
помечая такие ответы «Общие знания» и оставляя список цитат пустым. Имена PI,
численные результаты, оборудование, идентификаторы и публикации конкретного
эксперимента по-прежнему требуют подтверждения в найденных источниках.
На составной вопрос модель отвечает в доступной части и отмечает пробелы.
Наличие цитаты подтверждает существование фрагмента, а не автоматически
достоверность всех утверждений модели; карточки базы остаются вторичными источниками.

Аналитические вопросы допускают обоснованный вывод из нескольких фрагментов,
даже если готовой формулировки ответа нет в одном источнике. Модель должна
объяснить связь фактов, пометить интерпретацию, сослаться на исходные наблюдения
и указать ограничения вывода. Подробный запрос предполагает развёрнутое
объяснение, а не только перечисление найденного. Краткая карточка не считается
полным текстом статьи: выводы ограничены фактически загруженным материалом.
Перед текстом ответа модель составляет краткую карту наблюдений и пробелов
в служебном поле `evidence_assessment` того же JSON. Поле не попадает в
`ChatResponse` и интерфейс. Это способ направить генерацию, а не независимая
проверка достоверности: карта тоже может содержать ошибки. Дополнительного
вызова API не добавляется. Объяснение невозможности расчёта или неподтверждённого
вывода считается ответом; отсутствие точного идентификатора допускает отказ.
В терминологии учитываются различия между radiative и radial extinction,
non-premixed flames и Z_st; определения проверены по
[NASA Flame Design SRD](https://www1.grc.nasa.gov/wp-content/uploads/Flame_Design_SRD_20100401.pdf)
и [NASA NTRS](https://ntrs.nasa.gov/citations/20240003229).

Поиск резервирует часть кандидатов для явно названных исследований и выбирает
обзор программы для общего вопроса о ней. Контекст распределяется между
участниками сравнения. При запросе оборудования, результатов, условий или
идентификаторов приоритет получают соответствующие разделы карточек.
Переписывание применяется к контекстным уточнениям;
самостоятельный вопрос не дополняется предыдущей темой. При переписывании
используются только последние четыре сообщения пользователя: прежние ответы
ассистента могут содержать ошибки и не должны закрепляться в поисковом запросе.
Полный диалог остаётся доступен при генерации для уточнений и исправления ошибок.
Номера цитат проверяются
до отображения; групповые ссылки нормализуются, а если модель указала только
структурированный список ссылок, он отображается в конце ответа.
Когда ссылки уже стоят в тексте, итоговый список строится по ним; дубликаты и
неиспользованные допустимые номера в служебном массиве не отменяют весь ответ.
Несуществующие номера по-прежнему отклоняются. Ошибка проверки формата имеет
отдельное сообщение и причину в журнале, вместо сообщения об отсутствии данных.

Начальные параметры `RAG_CHUNK_TOKENS=400`, `RAG_CHUNK_OVERLAP=50`,
`RAG_CANDIDATE_LIMIT=20`, `RAG_CONTEXT_LIMIT=5`, `RAG_BATCH_SIZE=32`.
Для сравнений нескольких коротких карточек можно увеличить `RAG_CONTEXT_LIMIT`
до 12, сохраняя его не больше `RAG_CANDIDATE_LIMIT`.
`RAG_TIMEOUT` задаёт таймаут запроса к эмбеддингам и reranker.
`RAG_LLM_TIMEOUT` задаёт лимит основной модели (10 секунд по умолчанию).
При сбое или обрыве чат пробует `LLM_FALLBACK_MODEL` на том же провайдере,
если модель задана. Её лимит задаёт `RAG_LLM_FALLBACK_TIMEOUT` (8 секунд).
Сервер ограничивает обработку вопроса в чате 25 секундами.
`RAG_RETRIES` задаёт число повторов для эмбеддингов. Для внешнего `/rerank` укажите
`RERANKER_MODEL` и при необходимости параметры отдельного сервиса.
Без reranker или при его недоступности используется порядок pgvector.

Регрессии поиска, смены темы, общих объяснений и цитат проверяются вместе с
остальными тестами. Для проверки реальных API после загрузки ключей выполните
`python -m scripts.evaluate_answers`: скрипт использует только вымышленные
карточки ORION/LYRA, не обращается к рабочей БД и показывает время и результат
каждого сценария. Это отдельная ручная проверка, расходующая API-токены.

Для проверки устойчивости к навязыванию фактов, командам внутри источников,
ошибкам истории и сложным научным выводам:

```bash
python -m scripts.evaluate_robustness --output /tmp/ignis-robustness.json
python -m scripts.evaluate_robustness --case poisoned_history --repeat 2 --output /tmp/ignis-history.json
```

Скрипт использует 24 сценария с вымышленными исследованиями TEST-A/B/C,
FLUX и RANDOMIZED (включая расчёт массового потока и границы причинного вывода),
реальную настроенную LLM и код подготовки/проверки ответа приложения. БД,
внешние эмбеддинги и reranker не вызываются; fallback отключён для однозначного
сравнения моделей. `--model` меняет модель только для проверки, не для чата.
JSON сохраняет исходные ответы, итог приложения, критерии каждого сценария,
время и хеш промпта. Ключи не записываются. Допустимые номера цитат не означают
правильность выводов: поле `review=pending` требует ручной оценки содержания.
Ошибки провайдера учитываются отдельно и не считаются успешными проверками.

Карточки импортируются как вторичные источники. Реестр даёт ссылку на портал
NASA NTRS и идентификатор публикации, который сохраняется в названии источника.
Чанки сохраняют раздел Markdown и страницу PDF, если она существует.
Для других документов используйте существующий импорт с
`--documents manifest.json`. Манифест сопоставляет slug и ключ источника с
файлом относительно манифеста, например
`{"flex-1":{"report":"docs/report.pdf"}}`. Поддерживаются PDF с текстовым
слоем, Markdown и TXT. При сборке Docker таблица токенизации загружается
заранее. На хосте tiktoken кеширует её при первой индексации.

```bash
curl -fsS http://127.0.0.1:8000/api/v1/assistant/chat \
  -H 'Content-Type: application/json' \
  -d '{"message":"Какие выводы приводит карточка FLEX-1?","study_id":"flex-1"}'
```
